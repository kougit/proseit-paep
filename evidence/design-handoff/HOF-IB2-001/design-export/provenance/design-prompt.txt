PAEP IB2 — CLAUDE DESIGN EXECUTION
DWP-IB2-001 + HOF-IB2-001 REVIEW CANDIDATE

You are working on the ProSEIT Angular Experience Platform (PAEP).

This is a CONTROLLED DESIGN STAGE.

You are NOT implementing Angular production code.

You are NOT approving your own design.

You are creating the formal design candidate that will later be reviewed by
the Product Owner / Solutions Architect and, only if accepted, handed to
Claude Code for implementation.

==================================================
1. GOVERNING CONTEXT
==================================================

Use the supplied:

01-DESIGN-PREPARATION.md

as the immediate design-preparation input.

Also consult the current controlled PAEP sources available to you, especially:

- PAEP controlled platform specification;
- PAEP Implementation Architecture / Repository Baseline;
- PAEP Design-to-Code Handoff Standard;
- PAEP Claude Engineering Execution & QA Protocol;
- current approved ProSEIT branding sources if available.

==================================================
2. DESIGN WORK PACKAGE
==================================================

Create:

DWP-IB2-001
PAEP Design Foundations, Core Components and UI Laboratory

The design objective is to establish the first independent PAEP visual and
interaction language for:

- @proseit/paep-foundation;
- the approved first @proseit/paep-components tranche;
- apps/ui-lab.

This design must be:

- product-neutral;
- enterprise-grade;
- clean and professional;
- suitable for data-heavy applications;
- responsive;
- accessible;
- suitable for African enterprise operating environments;
- independently designed;
- reusable across manufacturing, agriculture, construction and other future
  ProSEIT products.

Do NOT imitate:

- Ultima;
- PrimeNG commercial templates;
- SAP Fiori;
- Material commercial themes;
- any proprietary dashboard/template product;
- screenshots of existing commercial enterprise systems.

Capability inspiration is acceptable.
Visual or implementation imitation is not.

==================================================
4. FOUNDATION DESIGN
==================================================

Design the complete candidate foundation system.

You must explicitly define candidate values and rationale for:

A. COLOUR

- neutral palette;
- page background;
- surface backgrounds;
- raised surfaces;
- text hierarchy;
- borders/dividers;
- brand accent;
- accent foreground/on-accent;
- success;
- warning;
- error;
- information;
- focus;
- selected;
- disabled;
- read-only.

Separate:

BRAND TOKENS

from:

SEMANTIC STATE TOKENS.

Brand overrides must never redefine:

- success;
- warning;
- error;
- information;
- focus;
- disabled;
- validation semantics;
- text contrast rules.

For every important foreground/background pair, provide contrast evidence.

Target WCAG 2.2 AA.

--------------------------------------------------
B. TYPOGRAPHY
--------------------------------------------------

Define:

- font strategy;
- body font;
- heading hierarchy;
- type scale;
- weights;
- line heights;
- letter spacing where required;
- numeric/data presentation;
- tabular numeral strategy;
- truncation/wrapping rules.

ZERO-NEW-DEPENDENCY PREFERENCE:

Prefer a high-quality system font stack unless there is a compelling
controlled reason to introduce a self-hosted open-licence font.

If you propose a third-party font:

do not treat it as approved.

Create:

DEPENDENCY / ASSET DECISION REQUIRED

with licence, source and rationale.

--------------------------------------------------
C. SPACING
--------------------------------------------------

Define:

- base spacing unit;
- spacing scale;
- inline spacing;
- block spacing;
- component padding;
- page/container spacing;
- responsive adjustments.

Avoid arbitrary one-off spacing.

--------------------------------------------------
D. SIZE
--------------------------------------------------

Define:

- control heights;
- icon dimensions;
- minimum interactive dimensions;
- density-specific dimensions.

Preserve accessibility target-size requirements.

--------------------------------------------------
E. RADIUS
--------------------------------------------------

Define a restrained radius scale.

Do not produce decorative excess.

==================================================
5. SURFACES AND ELEVATION
==================================================

Define semantic layers for:

- page;
- panel;
- card;
- raised card where justified;
- popover;
- drawer;
- dialog/modal.

Elevation communicates hierarchy, not decoration.

Prefer clarity and restrained depth.

==================================================
6. MOTION
==================================================

Define:

- which interactions use motion;
- durations;
- easing;
- entry/exit behaviour;
- loading motion;
- progress motion;
- skeleton motion.

Also define the complete:

prefers-reduced-motion: reduce

experience.

Under reduced motion:

- non-essential transitions disappear;
- shimmer becomes static;
- indefinite decorative animation disappears;
- essential state change remains understandable.

==================================================
7. RESPONSIVE SYSTEM
==================================================

Define candidate breakpoint/layout rules for:

- wide desktop;
- constrained desktop;
- tablet;
- mobile/narrow;
- 320 CSS-pixel reflow.

Also test conceptually at:

- 200% zoom;
- 400% zoom;
- long labels;
- approximately 2× text expansion;
- RTL.

Do not design a desktop layout and simply shrink it.

Design adaptive behaviour.

==================================================
8. DENSITY
==================================================

Design two density profiles:

COMFORTABLE
and
COMPACT

Define:

- spacing;
- control heights;
- row heights;
- component padding;
- intended usage.

Compact mode must not sacrifice:

- focus visibility;
- labels;
- accessibility;
- practical target size.

Choose one candidate default and justify it.

==================================================
9. FOCUS AND INTERACTION STATES
==================================================

Define a consistent visible focus system.

Specify:

- focus colour;
- thickness;
- offset;
- geometry;
- behaviour against light/dark surfaces.

Design interaction states for:

- default;
- hover;
- focus-visible;
- active/pressed;
- selected;
- disabled;
- read-only;
- invalid;
- loading.

No essential meaning may rely on colour alone.

==================================================
10. ICONOGRAPHY
==================================================

Define the desired icon vocabulary characteristics:

- stroke/fill model;
- optical weight;
- standard sizes;
- alignment;
- semantic use;
- directional mirroring;
- accessible-name rules.

ZERO-NEW-DEPENDENCY PREFERENCE:

Do not assume a third-party icon dependency is approved.

Either:

A. define an independently controlled PAEP icon approach;

or

B. recommend a named open-source icon set and produce a formal
DEPENDENCY / ASSET DECISION REQUIRED section containing:

- package/source;
- exact licence;
- self-hostability;
- reason;
- alternatives;
- implications.

Do not silently bind the design to a third-party icon library.

proseit-default

14. BUTTONS / ACTIONS
==================================================

- primary;
- secondary;
- tertiary;

- default;
- hover;

- active;

- loading;
- long-label;
- narrow-width.

==================================================
15. FORMS
==================================================

Design field anatomy covering:

- visible label;
- required indication;
- help text;
- error text;
- control;
- optional prefix/suffix;
- disabled;
- read-only;
- invalid;
- focus;
- long label/help/error.

Placeholder text must never replace a label.

Design validation for programmatic error association.

==================================================
16. TABLE SHELL — IMPORTANT DESIGN DECISION
==================================================

This is a D1 design decision.

Create and compare at least three narrow-screen strategies:

A. PRIORITY COLUMNS + ROW DETAIL

B. RESPONSIVE CARD/SUMMARY TRANSFORMATION

C. BOUNDED INTERNAL HORIZONTAL SCROLL

Evaluate each against:

- enterprise usability;
- 320 CSS-pixel reflow;
- information loss;
- keyboard access;
- accessibility;
- implementation complexity;
- scalability to data-heavy products.

Select one PRIMARY PAEP strategy.

You may retain another as a controlled fallback where genuinely justified.

Do not permit page-wide horizontal scrolling.

The table shell itself remains backend-neutral.

==================================================
17. ACTION GROUP RESPONSIVE DESIGN
==================================================

At wide widths:

show appropriate actions directly.

At narrow widths:

- preserve the primary action;
- move secondary actions into overflow where appropriate;
- retain destructive-action clarity;
- preserve keyboard accessibility;
- do not make hover the only discovery mechanism.
