2. OBJECTIVE
==================================================

Design the shared, product-neutral PAEP enterprise application shell that
every ProSEIT product will compose in its own thin app:

- topbar (product identity, tenant/site context, search/command entry,
  notifications, help, locale, account);
- sidebar navigation (driven by an app-supplied typed build-time
  manifest; groups, current state, collapsed mode, narrow/mobile
  navigation, long labels, RTL, locked explanations);
- workspace / page frame (title, context, status, primary/secondary
  actions, breadcrumbs when justified, filter region, generic extension
  and action regions, density, long content);
- search / command palette (bounded commands, grouped results, all states);
- notification access and panel (transient vs persistent);
- error boundary and not-found (correlation reference, retry, safe
  navigation);
- locked / unavailable presentation (permission, edition, configuration,
  environment/capability — each distinct);
- connectivity indicator (online, offline, degraded, unknown);
- a GENERIC workspace/page-frame hosting example that shows future
  experiences can be hosted through the generic regions;
- shell-local preference surfaces for the session only (navigation
  collapsed, density);
- one governed reusable positioning/menu base for shell menus (DDR-02).

The shell must use the accepted PAEP design system. Reuse existing PAEP
components and tokens wherever they exist. Do not restyle, duplicate or
privately substitute an existing primitive.

Package placement:
- reusable generic primitives (for example generic Menu/Popover
  behaviour)            → @proseit/paep-components
- generic design assets and icons → @proseit/paep-foundation
- shell compositions (topbar, navigation rail/sidebar, workspace/page
  frame, command-palette composition consuming approved generic
  primitives)           → @proseit/paep-enterprise

Generic primitives must NOT be designed as private substitutes inside
@proseit/paep-enterprise.

Where the shell needs something the design system does not have (for
example: inline-end alignment for PaepPopover, a general menu, a
combobox/listbox, a count badge, a search-field variant, an
"unavailable" empty-state kind, a skip link, shell icons, sidebar and
topbar layout tokens), mark it

PROPOSED NEW PATTERN

with the target package, the DCH class (D1/D2), the rationale, and why an
existing component cannot be used. None of these is authorised until the
PO/SA design review approves it.

3. MANDATORY CONSTRAINTS
==================================================

3.1 Product neutrality and synthetic content
- Use only the synthetic content in DWP-IB3-001 §12 ("Acme Platform",
  "Northwind Holdings — Site 04", "Alex Morgan", navigation groups
  Overview / Records / Operations / Reports / Administration, and their
  long, Arabic and Hebrew variants). "Reports" is a neutral label only.
- No manufacturing, agriculture, construction, fiscal, AI, IoT or other
  domain menu, vocabulary or workflow.
- No customer data and no real tenant or user data.

3.2 Backend authority (the shell presents; the server decides)
- Navigation visibility, disabled actions, edition presentation, command
  results, tenant context, preferences and deep links NEVER grant
  authority. Show them as provider-supplied state.
- Do not design or imply backend search, notification, identity,
  session, permission or entitlement contracts or services. Record the
  data you need as read-only data assumptions only.
- Locked-state and error copy must explain without implying that the
  browser enforces anything.
- Error UI shows fixed text and a correlation reference only — never
  stack traces, payloads, tokens or internal URLs.
- A tenant switch is a request; a deep link to another tenant never
  switches silently. Impersonation is always visible.
- Applications own their Routes. The enterprise shell may offer
  route-targetable shell, error, locked and not-found components, but it
  is never the route authority and has no permission-granting guards.
- Keep any prototype logic non-authoritative (PAEP-DCH-01 §7(vi)).

3.3 Scope
- No login page, reauthentication or real session/authentication flow.
  The account surface shows sign-out and the session state it is given.
- No offline queue, replay, service worker, conflict engine or sync
  authority, and no state or copy implying they exist.
- No analytics or reporting behaviour: no datasets, reporting gateways,
  metrics, drill-down, saved report definitions, saved views, report
  persistence or analytics navigation. The hosting example is generic.
- No preference persistence; shell preferences hold for the session only.
- No runtime-configuration schema change; navigation content comes from
  an app-supplied typed build-time manifest.
- i18n boundary: active locale, direction, lang/dir, message keys with
  English defaults. No dictionary loading, no complete locale-switching
  subsystem, no date/number/currency formatting subsystem. A locale
  selector appears only when the host supplies more than one locale, and
  it only raises a request to the app.
- Observability boundary: error reporting with a correlation reference
  only; no telemetry transport or metrics.
- No new dependencies.
- Do not create or propose Generation 5, baseline-registry entries or
  work-package records; that happens only after HOF approval.

3.4 Accepted DDR constraints (see the attached records)
- DDR-01: the table narrow rule depends on the content CONTAINER width
  (< 40 rem), so a sidebar can trigger it at desktop widths.
- DDR-02: today PaepPopover opens from the trigger's inline-start edge;
  there is no inline-end option and no general menu. Design all shell
  menus on ONE governed reusable positioning/menu base. The preferred
  direction is a PROPOSED extension of PaepPopover with inline-end
  alignment, also used — where technically and behaviourally
  appropriate — to rebuild the Action-group overflow. In SCR-SHELL-023
  show: inline-start; inline-end; collision flip/shift; LTR; RTL;
  keyboard/focus; dismissal; mobile behaviour. Do NOT design a third
  ad-hoc popover="manual" implementation in the enterprise package.
- DDR-04: an overflowing dialog/drawer body becomes a focusable region;
  page scroll is locked while a modal is open; use document scrolling.
- DDR-05: long non-interactive popover content takes focus; keep help
  popovers short.
- DDR-07: the F07 and R03 boards in HOF-IB2-001 v1.1 are the approved
  focus-state and 320 px references. Their UI-lab completion is later
  implementation work, not part of this design.
- DDR-08: modal footers use the dialog-footer pattern. Do not add
  role="group" automatically; propose it only for a concrete IB3 need,
  classified and justified.
- The checkbox error API (DDR-06 residual) is not to be introduced
  unless a concrete IB3 need is proposed, classified and justified.
- `paep-drawer` is not to be used as application navigation.

3.5 Public API form
- Every componentMap target uses a single public entry point per
  package, for example:
    @proseit/paep-enterprise#PaepShell
    @proseit/paep-components#PaepPopover
- Do NOT use @proseit/paep-enterprise/navigation or any other secondary
  or deep entry point.

3.6 Content keys
- All shell copy uses the controlled paep.shell.* message namespace, with
  typed English defaults and provider override, following the pattern
  the PAEP components already use.
