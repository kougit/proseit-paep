# IB4-FRAPPE-ADAPTER — Acceptance Criteria

All criteria are mandatory. They are the pre-flight acceptance criteria AC-IB4-01..22 ("PAEP IB4 — PRE-FLIGHT READINESS" §11), adopted by the PO/SA implementation authorisation of 2026-10-15 (§19) and clarified here only to make them testable. No criterion may be deleted, weakened, bypassed or rewritten to obtain PASS. PASS is technical; ACCEPTED is the PO/SA's decision. AC-IB4-22 is not a Claude criterion.

| ID | Area | Criterion | Verification |
| --- | --- | --- | --- |
| AC-IB4-01 | Port conformance | `@proseit/frappe-sdk` implements every IB4 contract port (session, records, workflow, files, capabilities, freshness, compatibility) and passes conformance against the recorded, versioned fixture backend (D2) | `qa:integration` conformance suite over every fixture case; fixture manifest check |
| AC-IB4-02 | Session / CSRF | Session responses map exactly to `SessionOutcome` (authenticated, unauthenticated, expired, invalid); every state-changing request (POST, PUT, PATCH, DELETE) carries the CSRF header and fails closed without it; the token is held in memory only; sign-out is server-authoritative; no bearer token; credentials only to the backend origin | `qa:frappe` session/CSRF tests and adversarial negatives (D3) |
| AC-IB4-03 | Lists / detail | List and detail reads are typed and cursor-paged through an approved compiled resource map; unknown resources, fields or operators are rejected before any request; no arbitrary DocType access | `qa:frappe` records tests; static check that no DocType name leaves the resource map |
| AC-IB4-04 | Workflow | Allowed actions come from the server; a transition outside the latest server set is refused before any request; the server decides; denial maps to an authorization error | `qa:frappe` workflow tests and negatives |
| AC-IB4-05 | Files | File access uses only server-provided, origin-checked URLs (no client-constructed path; foreign origin, protocol-relative, script, data, credentialed or traversal URLs rejected); metadata carries the server checksum when present | `qa:frappe` file tests and negatives |
| AC-IB4-06 | Errors | Every failure normalises to `PaepError` (code, messageKey, category, retryable, correlationId, fieldErrors); no raw server message, `_server_messages`, `exc` or stack trace reaches the error, a report or a log | `qa:frappe` error-normalisation tests and negatives |
| AC-IB4-07 | Concurrency / idempotency | A stale concurrency token maps to `conflict`; a retried write keeps its idempotency key; only retryable failures are retried, with a bounded count | `qa:frappe` concurrency tests and negatives |
| AC-IB4-08 | Freshness | Polling produces invalidation signals only; a signal never carries authoritative data; consumers reconcile through an authoritative read; recovery and reconnect trigger reconciliation; polling is bounded | `qa:frappe` freshness tests and negatives (D4) |
| AC-IB4-09 | Compatibility | `pmra-api-v1` check: compatible backend proceeds; known-incompatible backend is blocked; unknown or unverifiable compatibility is blocked and surfaced through the approved PAEP failure state | `qa:frappe` compatibility tests over the fixture profiles (D10) |
| AC-IB4-10 | Observability | Correlation ids propagate on every request and into every `PaepError`; error reports are sanitised (no token, cookie or PII) | `qa:frappe` correlation and privacy tests |
| AC-IB4-11 | Package boundaries | No dependency-direction change; the adapter imports only permitted packages; only applications import it; enterprise, components, foundation, analytics and domain packages never do; no Frappe type leaks through a public PAEP contract | `qa:architecture`; `qa:enterprise` E01; `qa:frappe` static checks; seeded negatives |
| AC-IB4-12 | Contract additions | Additions only, in `@proseit/paep-contracts`; framework-, Frappe-, DOM- and transport-neutral; the API snapshot is updated, reviewed and identical on re-run | `qa:contracts` S1-S10 with the new positives and negatives |
| AC-IB4-13 | Frozen surfaces | No runtime-config schema change, no dependency or lockfile change, no engine change, no CI timeout change | `qa:enterprise` E09; IB0-WP05 W06 and W11; seeded negatives |
| AC-IB4-14 | Security negatives | Every negative of pre-flight §10 and authorisation §15 is present and fails for its intended reason | `qa:frappe` negatives; `qa:enterprise:negative`; `qa:ib4:ci-negative` |
| AC-IB4-15 | Gate rescoping | E01, E09, E10 and the WP05 filled-entry controls keep their strictness outside the Generation 6 scope, with pre- and post-promotion proofs for every rescoped, baseline-relative check | `qa:enterprise:negative` positives and negatives against synthetic baselines |
| AC-IB4-16 | CI | `PAEP / frappe-adapter` is mandatory and registered in every gate and policy mechanism; removing it fails closed; all mandatory checks are green on the exact head | CI run on the exact head; `qa:ib4:ci-negative`; WP05 partition |
| AC-IB4-17 | Regression | IB0-IB3 gates are unchanged in strictness and green | full CI, including every accepted job |
| AC-IB4-18 | Clean room / secrets | No secret, credential, cookie value or token anywhere; no proprietary template or third-party source; provenance recorded | `qa:frappe` secret and provenance checks; IB0-WP05 W08; provenance register |
| AC-IB4-19 | Records | Traceability, evidence and the acceptance report are complete and accurate | `TRACEABILITY.csv`; `ACCEPTANCE_REPORT.md`; `evidence/IB4-FRAPPE-ADAPTER/` |
| AC-IB4-20 | Carried obligations | PAEP-LOC-AR-PILOT, PAEP-LOC-HE-PILOT and PAEP-A11Y-AT-PILOT stay OPEN; IB4 adds no user-visible copy or interaction | `work-package.json`; `qa:frappe` and `qa:enterprise` no-new-copy checks |
| AC-IB4-21 | Independent QA | An independent QA pass on the exact candidate head finds HIGH = 0 and MEDIUM = 0 open | independent QA report under `evidence/IB4-FRAPPE-ADAPTER/` |
| AC-IB4-22 | Human acceptance | The PO/SA accepts IB4 | PO/SA decision (not a Claude criterion) |
